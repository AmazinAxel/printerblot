# Calibrating Blot — speed and acceleration

(disclaimer: these docs are generated by Claude and used for reference by it. It is accurate, feel free to read it!)

This is the spec for a **web-based calibrator**, not yet built. It replaces `tune.py`, a USB script that drove the same procedure over serial before USB input was removed from the firmware. Everything here is what that tool did and why; the web version should do the same through the board's web UI.

The limits in `$110`/`$112`/`$120`/`$122` decide how fast the machine can plot before it starts skipping steps. The compiled-in defaults (`src/config.h`) are the *measured* limits of one particular Blot, not conservative starting points, so on a machine with different belts, motors or driver current they may be too high. Calibrating finds the machine's real ceiling and backs off to a safety margin.

> Calibrate after building or re-tensioning a machine, *before* running real
> art. A skipped step isn't recoverable mid-drawing — the rest of the plot is
> offset.

## The settings

Settings keep GRBL's `$` numbering as their ids (`settings_set(id, value)` in `src/settings.h`). They persist to flash and are validated: speeds and accelerations must be `> 0`, only `$130`/`$131` may be negative.

| Id     | Space     | Meaning                                         | Calibrated by |
| ------ | --------- | ----------------------------------------------- | ------------- |
| `$110` | Cartesian | Max tip feedrate (mm/min)                       | Test A        |
| `$111` | Cartesian | Max rapid (G0) feedrate (mm/min)                | derived       |
| `$112` | Motor     | Max rate of an individual motor (mm/min)        | Test B        |
| `$120` | Cartesian | Max tip acceleration (mm/s²)                    | Test C        |
| `$122` | Motor     | Max individual-motor acceleration (mm/s²)       | Test D        |
| `$140` | Cartesian | Junction deviation (mm) — corner rounding       | quality preset |
| `$130`/`$131` | Machine | Work envelope X/Y (mm), soft limits      | by hand       |
| `$20`  | —         | Soft limits on (1) / off (0)                    | by hand       |
| `$150`/`$151` | Servo | Pen up / down pulse width (µs)            | by hand       |

## Why four numbers, not two

Blot is CoreXY, so the same Cartesian move loads the motors differently depending on direction (`a = x − y`, `b = −x − y`):

| Tip direction | What the motors do                                  | Bottleneck          |
| ------------- | --------------------------------------------------- | ------------------- |
| Pure X or Y   | **Both** turn at tip speed                          | Neither — a tie     |
| ±45° diagonal | **One** turns at `√2×` tip speed, the other is still | The spinning motor |
| Anything else | A mix                                               | Whichever is closer to diagonal |

Per block the planner computes the motor load (1 axis-aligned, √2 diagonal) and clamps speed to `min($110, $112 / load)` and acceleration to `min($120, $122 / load)`. So pure X/Y are the *fastest* directions and ±45° the slowest — the opposite of a Cartesian machine — and a limit found by pushing pure X is too high for diagonals. Hence a Cartesian cap and a motor cap for each quantity, each measured by its own test.

## Why it has to be measured

Steppers give no warning before they skip: one moment they follow the commanded motion, the next torque drops out and they slip. The firmware's position counter tracks *commanded* steps, not real rotation, so it can't detect a skip either. The test is physical — the pen drifts on paper, and the user sees it:

1. Set a candidate cap.
2. Run a pattern that should return to its start.
3. Ask the user whether the pen came back to its starting dot, with no grinding or stalls.
4. If not, the motors skipped — back off. If so, push higher and repeat.
5. At the cliff, save **80%** of the last passing value, so jitter, ink drag and temperature don't creep back over the edge.

## The procedure

### Setup (shown to the user)

1. A pen in the holder, paper taped down.
2. Leave ~120 mm of free travel in `+X` and `+Y` from the start point (axis tests run 100 mm, diagonals ~71 mm).
3. Start from a fresh power-up, or from the machine origin: soft limits measure *machine* coordinates, which are (0, 0) at power-on, so a start point far out on the bed trips the envelope even with room on the paper.

First the calibrator marks the origin: `G21`, `G90`, `G92 X0 Y0`, pen down, a short pause, pen up — a dot every test should return to.

### Tests — accelerations first

Order **C → D → A → B**. A speed test at low acceleration never reaches its commanded feedrate (a triangle profile, `v_peak = √(a·L)`), so every "yes, faster" would be a false positive measuring the accel cap. Accelerations are found first and then held while speeds are tested.

| Test | Tunes  | Pattern (repeated 3×, from the origin)        | Other caps pushed out of the way |
| ---- | ------ | --------------------------------------------- | -------------------------------- |
| C    | `$120` | `G1 X20 F999999`, `G1 X0` — axis accel hops   | `$110`, `$112`, `$122` uncapped  |
| D    | `$122` | `G1 X14 Y14 F999999`, `G1 X0 Y0` — diagonal   | `$110`, `$112`, `$120` uncapped  |
| A    | `$110` | `G1 X100 F<v>`, `G1 X0` — axis top speed      | `$112` uncapped; `$120`/`$122` = C/D results |
| B    | `$112` | `G1 X50 Y50 F<v>`, `G1 X0 Y0` — diagonal speed | `$110` uncapped; `$120`/`$122` = C/D results |

"Uncapped" means a huge value (999999999) so only the setting under test can bind; otherwise a low `$112` would silently cap `$110` during Test A and every answer would be meaningless.

Each pattern runs as a job wrapped in: `G21`, `G90`, `G92 X0 Y0`, pen down, the pattern, pen up.

### The search, per test

- Start at the stored value (never below the compiled default: 16606 for accelerations, 16401 for speeds).
- After each run ask: **pen returned cleanly, no stalls?** — yes / no / retry the same value / quit this test.
- Yes: multiply by the growth factor and run again. No: stop.
- Save `backoff ×` the last passing value. No passing value: leave the setting as it was.
- Coarse mode: growth ×1.5, backoff 80%. **Fine** mode (run after a coarse pass): start at 0.95× the stored value, growth ×1.1, backoff 90% — lands within ~5% of the real cliff.

What counts as "no": the pen visibly off its dot (step loss); grinding or clacking during a move (the motor is at the edge of stalling); stopping short or overshooting.

### Afterwards

- Write each tuned value; restore every cap that was pushed out of the way but not tuned to its original value.
- Set `$111 = min($112, max($110, stored $111))`: travel at least as fast as drawing, never asking a motor for more than its tuned rate.
- Pen up, release the motors, and show old → new values.

## Firmware support it will need

None of this exists yet; the board currently only accepts whole jobs. The calibrator needs, roughly:

- **Read and write settings** — an endpoint over `settings_set()` + `settings_save()`, returning the current values (the quality presets already go through the same functions).
- **Run a pattern** — upload it as a job and start it, then learn when it has finished (the existing job state over SSE does this).

Quality presets (`job.cpp`) are derived from the measured values: they keep the motor caps `$112`/`$122` and only move the Cartesian caps and `$140`.

## Numbers to sanity-check against

| Setting | Conservative | Aggressive | Measured on this machine |
| ------- | ------------ | ---------- | ------------------------ |
| `$110`  | 3000         | 9000       | 19682                    |
| `$112`  | 3000         | 12000      | 13121                    |
| `$120`  | 500          | 2000       | 29890                    |
| `$122`  | 500          | 2500       | 19927                    |

A well-tensioned Blot with a light carriage has far more headroom than a generic gantry; don't copy the right-hand column onto another machine without measuring. Note that with `$112` = 13121 a 45° diagonal tops out at 13121/√2 ≈ 9280 mm/min however high `$110` goes.
