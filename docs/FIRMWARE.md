# Blot GCODE Firmware

(disclaimer: these docs are generated by Claude and used for reference by it. It is accurate, feel free to read it!)

A minimal, GRBL-protocol-compatible G-code firmware for the Blot pen plotter,
plus the web UI that drives it. Runs on a **Seeed XIAO ESP32-S3** with A4988
drivers and a servo pen-lift.

Source files live in `src/`. Build with PlatformIO from the repo root.

## Goals, in priority order

1. **Accuracy.** It's a pen plotter. Never lose a step. Corners hit their
   programmed position. Arcs are round.
2. **Standalone operation.** The board hosts its own web UI and stores the
   job in flash. No connected computer, no daemon, no serial babysitter.
3. **A small, honest serial protocol.** GRBL-*shaped* (`ok`/`error:n`, `$`
   settings, `?` status) because that's a sound convention, but third-party
   sender compatibility was deliberately dropped — the only consumer is the
   vendored `tune.py`.
4. **Simple.** Readable in an afternoon.

## Hardware assumptions

The XIAO ESP32-S3 drops into the Blot control board's XIAO headers; the
`D0`-`D10` aliases map to the same physical pads as the RP2040 XIAO it
replaced, so the wiring is unchanged.

| Signal          | Pin  | Note                                    |
|-----------------|------|-----------------------------------------|
| Motor 1 STEP    | D10  |                                         |
| Motor 1 DIR     | D9   |                                         |
| Motor 2 STEP    | D8   |                                         |
| Motor 2 DIR     | D7   |                                         |
| Driver ENABLE   | D1   | active LOW                              |
| Pen servo       | D6   | = GPIO43; timer-driven, not PWM         |

CoreXY mixing: `motor1 = x + y`, `motor2 = y − x`. A4988 16× microstepping
with 20-tooth GT2 pulleys on 2 mm-pitch belt → **80 microsteps/mm**.

USB CDC is enabled on boot, so `Serial` is the native USB port and UART0
(GPIO43/44 = D6/D7) is free for ordinary GPIO — which is what lets the servo
and motor 2 direction sit there.

## Why the servo isn't PWM

D6 is GPIO43, hardwired to UART0. The LEDC PWM matrix can't route to it
(ESP32Servo's own pin table excludes 43 and 44), so the usual Servo library
hangs in `attach()`. The board can't be rewired, so `penservo.cpp` generates
the 50 Hz pulse from timer group 1 and a plain GPIO write instead — two
interrupts per 20 ms frame, with milliseconds of jitter tolerance.

The pulse train **stops** once the pen has had time to arrive
(`SERVO_HOLD_MS`, 400 ms). A hobby servo only holds position while pulsed,
and holding is its worst case: it hunts around the setpoint, buzzing and
wearing the gear train. The pen rests either up or down under no load, so
there's nothing to hold. The next `penservo_write_us()` restarts the train.

## Concurrency model

Two cores, and the split matters:

| Core | Runs                                                          |
|------|---------------------------------------------------------------|
| 0    | WiFi, TCP, the async web server, mDNS                         |
| 1    | Arduino `loop()`: gcode parser, job feeder — and the step ISR  |

The step timer ISR is registered with `ESP_INTR_FLAG_IRAM` and every function
it reaches is `IRAM_ATTR`. That's not decoration: a flash cache miss (which
any WiFi or LittleFS write can cause) would stall step generation for tens of
microseconds and show up as a visible stutter. Two consequences that are easy
to reintroduce by accident:

- **No floating point in the step ISR.** Xtensa FreeRTOS allocates the FPU
  lazily per task and doesn't save coprocessor state across interrupts, so a
  float op raises EXCCAUSE 4 as soon as another task owns the FPU. All the
  velocity math there is 64-bit integer, including a hand-rolled `isqrt()`,
  because newlib's `sqrtf` lives in flash anyway.
- **No `digitalWrite`/`delayMicroseconds`/`gpio_set_level` in the ISR.** All
  three live in flash. `config.h` provides `isr_pin_write()` and
  `isr_delay_us()`, which poke the GPIO set/clear registers and the cycle
  counter directly.

HTTP handlers run on core 0 but never touch the parser. `/print`, `/pause`,
`/stop` and `/quality` just set a volatile flag; `job_service()` applies it
on core 1. Stop decelerates (feed hold) before flushing the planner.

In a job file, `M0`/`M1` pause the job (resumable from the web UI) rather
than feed-holding, and any failed line other than an unsupported command
aborts the job instead of being skipped.

## Supported G-code

See [SUPPORTED_COMMANDS.md](SUPPORTED_COMMANDS.md) for the full reference
with every word, error code and realtime byte. Summary:

- **Motion:** `G0` `G1` `G2` `G3` `G4`
- **Coordinates:** `G20` `G21` `G90` `G91` `G92` `G28`
- **Pen:** `M3 S<us>` (down), `M5` (up) — GRBL spindle commands repurposed
- **Machine:** `M17` `M18`/`M84` `M0`/`M1` `M2`/`M30`
- **Settings:** `$$` `$N=value` `$RST=*`
- **Realtime:** `?` `!` `~` `0x18`

Settings persist to flash (EEPROM emulation over a NVS partition), written
lazily: a `$N=` marks a dirty bit, and `settings_service_save()` flushes once
the stepper is idle and 500 ms have passed since the last change. That
coalesces a tuning script's burst of writes into one erase cycle, and keeps
the ~50 ms flash stall out of the middle of a move.

## Serial protocol (USB)

Line-oriented, one response per line:

- A line that parses OK → `ok\r\n`. Note this means *parsed and queued*, not
  *finished moving* — the planner buffers ahead.
- A parse error → `error:<n>\r\n` (codes in `StatusCode`, `config.h`).
- Realtime bytes (`?` `!` `~` `0x18`) are intercepted before the line buffer
  and produce no `ok`.

`tune.py` is a simple send-and-wait-for-`ok` client, which is all this needs
now. If the planner is full the parser blocks until a slot frees, so a fast
writer is naturally throttled rather than overflowing — except during a feed
hold, where it returns `error:60` instead of blocking forever.

Printing a real job doesn't use this path at all: the file is uploaded over
HTTP and `job.cpp` feeds it to the parser directly.

When a line has to wait for a planner slot (e.g. a long arc),
`protocol_wait_for_planner_slot()` keeps reading the port: `?`, `!` and `~`
act immediately, other bytes are set aside for the line reader, and Ctrl-X
abandons the blocked line (no `ok` for it) and resets. Every spin loop on the
planner must go through it — it is also what services pen/dwell sync blocks,
and a loop that skipped that deadlocked behind an `M3`.

## Planner invariants

- The newest block's entry speed is capped at `sqrt(2·a·L)`: it must be able
  to stop within itself, since nothing is queued after it.
- A block queued into an empty planner starts from rest — the machine has
  stopped, whatever the junction with the previous move would allow.
- The block the stepper is executing is never re-planned at its entry, and
  once it is decelerating its trapezoid is frozen; the next block's entry is
  clamped to that frozen exit instead. Either change would jump the step rate.
- After a feed hold, `~` ramps up from rest under the accel limit until it
  meets the planned profile.

## Motion architecture

```
  USB serial ──┐                    ┌── HTTP upload → LittleFS /job.gcode
               │                    │
               ▼                    ▼
        protocol.cpp           job.cpp  (feeds lines while the planner
        (line buffer,           has room — that headroom is what lets
         realtime bytes)        lookahead carry speed through corners)
               │                    │
               └────────┬───────────┘
                        ▼
                    gcode.cpp  → arc.cpp splits G2/G3 into segments
                        │
                        ▼
                planner ring buffer  ◀── reverse/forward passes
                    (16 blocks)          apply junction deviation
                        │
                        ▼
                stepper ISR (timer group 0, variable period)
                 one step event per fire
                 trapezoidal velocity profile per block
                 Bresenham mixing between motor1/motor2
                        │
                        ▼
                     STEP pins
```

### CoreXY-aware acceleration (this is the important part)

Blot is CoreXY-style: `motor1 = x + y`, `motor2 = y − x`. That means the same
motor acceleration does *not* produce the same Cartesian tip acceleration in
every direction. For a Cartesian move along direction `(dx, dy) / L`:

- `|A_per_tip| = |dx + dy| / L`  → 1 for axis-aligned, **√2 at 45°**, 0 for -45°
- `|B_per_tip| = |dy − dx| / L`  → 1 for axis-aligned, 0 at 45°, **√2 at -45°**

So if we naively clamp acceleration in motor space, the tip would have:

- Full programmed accel on pure X/Y moves (both motors at the same ratio)
- **1/√2 accel on ±45° diagonals** (because one motor has to move √2× as fast)
- A different accel again at every other angle

Discontinuous Cartesian accel at block boundaries = stepper cogging, belt
ringing, and visible corner artefacts. Not OK on a pen plotter.

**What this firmware does instead:**

1. Feedrates, junction deviation, and the trapezoidal profile are all planned
   in **Cartesian tip-space** (units: mm, mm/s, mm/s²). That's what the user
   cares about and what determines how the drawing *looks*.
2. Per block, we compute `max_motor_per_tip = max(|A_per_tip|, |B_per_tip|)`
   — how many motor-space mm the faster motor travels per Cartesian mm of
   tool path.
3. The block's effective Cartesian acceleration is clamped to
   `min($120, $122 / max_motor_per_tip)`. On axis-aligned moves this equals
   `$120`; on 45° diagonals it drops by 1/√2.
4. Likewise for speed: `min($110, $112 / max_motor_per_tip)`.
5. The stepper ISR generates "step events" at the rate the Cartesian profile
   asks for; Bresenham then distributes each event to motor1, motor2, both, or
   neither, based on the integer step deltas.

The net effect: along any straight line the tip accelerates at a single
constant rate, which may be lower than requested to respect physical motor
limits. Corners are handled by the junction-deviation model in Cartesian, so
cornering speed follows the *path* geometry, not the motor mix.

The planner runs two passes on every enqueue: a reverse pass clamps each
block's entry speed against what it can decelerate from, and a forward pass
clamps against what it can accelerate to. Straight from GRBL.

### Max-speed note

Because `max_motor_per_tip` is 1 on axes and √2 on diagonals (the inverse of
what a Cartesian printer does), pure X/Y moves are the *fastest* directions
on Blot; ±45° diagonals are the slowest. This is the opposite of most users'
intuition — keep it in mind when setting `$110`. See [TUNING.md](TUNING.md).

## Soft limits

There are no limit switches, so nothing physically stops the carriage — a
move past the frame is a crash at up to 16000 mm/min that the machine can
neither detect nor recover from. Soft limits are the only guard, and they're
on by default (`$20=1`).

The check lives in `plan_buffer_line()`, the one function every motion path
funnels through (G0/G1, each arc segment, G28, the job feeder), so there's no
route that can bypass it. Two details worth knowing:

- **Arcs are checked as a whole, before the first segment is queued.** An arc
  can bulge outside the envelope while both endpoints sit inside it. The test
  uses the exact bounding box — the two endpoints plus whichever of the four
  axis-crossing points the sweep actually passes through — so a rejected arc
  draws *nothing* instead of stopping half-way round.
- **Out of range rejects, it doesn't clamp.** Clamping would silently deform
  the drawing and carry on; a refusal stops at the first bad move with
  `error:15`. Inside a job, that aborts the print (and says so in the web UI)
  rather than skipping lines and producing a mangled image.

Limits apply to **machine** coordinates. `G92` moves the *work* origin, not
the machine's, so setting an origin in the middle of the bed genuinely
reduces how far you can draw — that's the constraint being reported, not a
bug. The envelope is `$130` × `$131`, default 125 × 125 mm, matching what
`tools/pdf2gcode.py` scales output to.

## Power and wear behaviour

Deliberate, because this machine is meant to be left plugged in:

- **Motors release when idle.** A stationary energised stepper is its worst
  thermal case — rated current, no back-EMF, no airflow — and a plotter has
  no gravity load to hold. `job.cpp` sends `M18` as soon as the planner is
  empty and the stepper is idle. Motion re-energises them automatically, and
  that enable is *queued through the planner* rather than written directly,
  so it can't fire while an earlier `M18` is still draining.
- **The servo stops pulsing** once the pen has arrived (see above).
- **WiFi modem-sleep while idle**, full power while printing. Sleep parks the
  receiver between beacons and saves a meaningful chunk of idle draw, but it
  adds tens of ms of latency, which would eat into the planner's buffer
  during a print.
- **`loop()` yields when there's nothing to do**, so FreeRTOS can idle the
  core instead of spinning at 240 MHz. Strictly gated on being idle.
- **Flash writes are coalesced** (see settings, above) — flash endurance is
  ~100k erase cycles, and an identical-value write is skipped entirely.

A task watchdog reboots the board if `loop()` wedges for 30 s. That's long,
deliberately: a `G4` dwell or a flash commit can legitimately block for a
while, and a spurious reboot mid-print is worse than a slow recovery.

## Building

```bash
pio run              # compile
pio run -t upload    # flash firmware
pio run -t uploadfs  # flash the web UI in data/ to LittleFS
pio device monitor   # serial monitor at 115200
```

`src/wifi_config.h` is required and gitignored — copy
`src/wifi_config.h.example` and fill it in. A missing file is a hard
`#error`, not a warning, because otherwise the board silently has no network
and it looks like a WiFi bug much later.

Partition layout is in `partitions.csv`: two 2 MB app slots (OTA-capable
layout, only app0 used today) and a ~3.5 MB LittleFS for the web assets and
the current job.

## Testing on bench before plotting

Before plugging a pen in:

1. Flash firmware, open a serial terminal at 115200.
2. Send `?` — should see `<Idle|MPos:0.000,0.000,0.000|FS:0,0>`.
3. Send `M17` then `G21 G90 G1 X10 Y0 F600` — carriage should move in X.
4. Send `G1 X0 Y0` — should return.
5. Send `G2 X20 Y0 I10 J0 F600` — semicircle; verify shape by hand-tracing.
6. Send `M3 S1350` / `M5` — servo should click between positions.

Until you've done steps 1–6, don't run real art through it.

## What this firmware deliberately does NOT do

- No limit switch handling (there aren't any)
- No probing (`G38`), no tool change, no coolant
- No spindle PWM (M3 is repurposed for the servo)
- No CoreXY auto-detection — hardcoded, this firmware is only for Blot
- No `$H` hard homing (there's nothing to home against)
- No EEPROM compatibility with GRBL's settings layout — settings IDs are
  GRBL-ish but values and semantics differ
- No *hard* limits (no switches to trip) — but soft limits ARE enforced, see
  below

If you need any of those, use stock GRBL-HAL on a board with the right I/O.

## Known limitations

Deliberate compromises, not bugs:

- **Feed hold decelerates across blocks** (the rate is rescaled per block via
  `events_per_mm_q8`), but parks at a sync block (pen, dwell) rather than
  running it mid-hold. The planner already brings speed to zero there.
- **Arc segments have a 0.5 mm floor** (`ARC_MIN_SEGMENT_MM`). A tight chord
  tolerance on a small arc would otherwise emit dozens of sub-mm segments
  that the planner can't build a ramp across. Well below what's visible.
- **`G92` offsets persist and accumulate** until `G92.1` clears them. Set a
  clean origin with `G92 X0 Y0` after positioning manually.
- **Soft reset (`0x18`) preserves motor position**, because on real hardware
  the motors are physically wherever they are. The planner is re-anchored to
  that position rather than to a phantom (0, 0).
- **Motor-step rounding is bounded at ±0.5 step.** The planner rounds each
  block's motor delta relative to the *absolute* target, not the per-segment
  delta, so endpoint error is ±0.00625 mm regardless of how many arc segments
  were emitted — no √N drift.
