# Blot GCODE Firmware

(disclaimer: these docs are generated by Claude and used for reference by it. It is accurate, feel free to read it!)

A minimal, event-driven G-code firmware for the Blot pen plotter, plus the web
UI that drives it. Runs on a **Seeed XIAO ESP32-S3** with A4988 drivers and a
servo pen-lift.

Source files live in `src/`. Build with PlatformIO from the repo root.

## Goals, in priority order

1. **Accuracy.** It's a pen plotter. Never lose a step. Corners hit their
   programmed position.
2. **Standalone operation.** The board hosts its own web UI and stores the
   job in flash. The web UI is the *only* interface: no USB or serial input,
   no connected computer, no daemon.
3. **Idle is free.** The machine is meant to be left on all year: nothing
   polls, nothing ticks, motors and servo go quiet, the CPU slows down.
4. **Simple.** Readable in an afternoon.

## Hardware assumptions

The XIAO ESP32-S3 drops into the Blot control board's XIAO headers; the
`D0`-`D10` aliases map to the same physical pads as the RP2040 XIAO it
replaced, so the wiring is unchanged.

| Signal          | Pin  | Note                                    |
|-----------------|------|-----------------------------------------|
| Motor 1 STEP    | D10  |                                         |
| Motor 1 DIR     | D9   |                                         |
| Motor 2 STEP    | D8   |                                         |
| Motor 2 DIR     | D7   |                                         |
| Driver ENABLE   | D1   | active LOW                              |
| Pen servo       | D6   | = GPIO43; timer-driven, not PWM         |

CoreXY mixing: `a = x − y`, `b = −x − y` (see `kinematics.h`). A4988 16×
microstepping with 20-tooth GT2 pulleys on 2 mm-pitch belt → **80
microsteps/mm**.

USB serial is switched off (`ARDUINO_USB_CDC_ON_BOOT=0`) and nothing starts
UART0, so its pads (GPIO43/44 = D6/D7) are ordinary GPIO — which is what lets
the servo and motor 2 direction sit there. Flashing still goes over USB: the
S3's USB-Serial-JTAG peripheral does that in hardware.

## Why the servo isn't PWM

D6 is GPIO43, hardwired to UART0. The LEDC PWM matrix can't route to it
(ESP32Servo's own pin table excludes 43 and 44), so the usual Servo library
hangs in `attach()`. The board can't be rewired, so `penservo.cpp` generates
the 50 Hz pulse from timer group 1 and a plain GPIO write instead — two
interrupts per 20 ms frame, with milliseconds of jitter tolerance.

Time on the pen is counted in those frames by the servo's own interrupt:
after a new target it flags the pen as arrived (~60 ms) and wakes the loop;
after 400 ms it stops re-arming itself and leaves the line low. A hobby servo
only holds position while pulsed, and holding is its worst case — it hunts
around the setpoint, buzzing and wearing the gear train — while the pen rests
up or down under no load. The next pen command restarts the train.

## Event model

Nothing in the firmware polls or waits on a timer. `loop()` sleeps in
`wake_wait()` (a FreeRTOS task notification) until something it must act on
has changed, then runs `stepper_service()` and `job_service()` once:

| Producer   | Wakes the loop when                                       |
|------------|-----------------------------------------------------------|
| Step ISR   | a planner slot frees, a pen block is reached, motion stops |
| Servo ISR  | the pen has arrived                                        |
| HTTP task  | print / pause / resume / stop / quality is requested       |

Wakes are counted, so one landing mid-pass isn't lost, and several coalesce
into one pass. Idle, nothing is armed at all: no step timer, no servo timer,
no wakes. The only deliberate wait left is a sub-2 µs spin inside the step
ISR — the remainder of the A4988's minimum STEP pulse after the ISR's own
math has run during it.

There is no task watchdog on `loop()`: it sleeps indefinitely by design, and
feeding a watchdog would need a periodic timer.

## Concurrency model

Two cores, and the split matters:

| Core | Runs                                                          |
|------|---------------------------------------------------------------|
| 0    | WiFi, TCP, the async web server, mDNS                         |
| 1    | Arduino `loop()`: gcode parser, job feeder — and both ISRs    |

The timer ISRs are registered with `ESP_INTR_FLAG_IRAM` and every function
they reach is `IRAM_ATTR` (including the FreeRTOS notify they wake the loop
with). That's not decoration: a flash cache miss (which any WiFi or LittleFS
write can cause) would stall step generation and show up as a visible
stutter. Two consequences that are easy to reintroduce by accident:

- **No floating point in the step ISR.** Xtensa FreeRTOS allocates the FPU
  lazily per task and doesn't save coprocessor state across interrupts, so a
  float op raises EXCCAUSE 4 as soon as another task owns the FPU. All the
  velocity math there is integer, including a hand-rolled `isqrt()`,
  because newlib's `sqrtf` lives in flash anyway.
- **No `digitalWrite`/`delayMicroseconds`/`gpio_set_level` in the ISR.** All
  three live in flash. `config.h` provides `isr_pin_write()` and
  `isr_delay_us_since()`, which poke the GPIO set/clear registers and the cycle
  counter directly.

HTTP handlers run on core 0 but never touch the parser: `/print`, `/pause`,
`/stop` and `/quality` set a volatile flag and wake the loop, which applies
it on core 1. Stop decelerates (feed hold) before flushing the planner.

## G-code

Only what the web UI's generators emit: `G0` `G1` `G21` `G90` `G92` `M3`
`M5`, plus `M0`/`M1` as a job pause. Harmless unknown codes are skipped;
anything that would misplace geometry (arcs, inches, relative mode...) or a
move outside the work area **stops the print**. See
[SUPPORTED_COMMANDS.md](SUPPORTED_COMMANDS.md).

A line can queue at most `MAX_BLOCKS_PER_LINE` (3) planner blocks — two pen
commands and a move — and the job feeder only parses a line when that many
slots are free. So queueing never fails for lack of room and nothing ever
waits for a slot: when the planner is full the loop simply sleeps until the
step ISR frees one.

## Settings

Persisted to flash (EEPROM emulation over the NVS partition) by
`settings_save()`, which skips the write when nothing changed — flash is
~100k erase cycles and the UI re-sends the whole quality preset on every
toggle. Today only the quality presets change settings; the planned web
calibrator will too ([CALIBRATION.md](CALIBRATION.md)). A flash write stalls
the loop for tens of ms, which is harmless: the step ISR runs from IRAM
through it, and a full planner covers far longer.

## Planner invariants

- The newest block's entry speed is capped at `sqrt(2·a·L)`: it must be able
  to stop within itself, since nothing is queued after it.
- A block queued into an empty planner starts from rest — the machine has
  stopped, whatever the junction with the previous move would allow.
- The block the stepper is executing is never re-planned at its entry, and
  once it is decelerating its trapezoid is frozen; the next block's entry is
  clamped to that frozen exit instead. Either change would jump the step rate.
- Lookahead only re-plans from the newest block whose entry is final
  (`buffer_planned`, GRBL's optimal-plan pointer).

## Motion architecture

```
  HTTP upload → LittleFS /job.gcode
                    │
                    ▼
                job.cpp  (feeds lines while the planner has room —
                    │     that depth is what lets lookahead carry
                    │     speed through corners)
                    ▼
                gcode.cpp
                    │
                    ▼
            planner ring buffer  ◀── reverse/forward passes
                (16 blocks)          apply junction deviation
                    │
                    ▼
            stepper ISR (timer group 0, variable period)
             one step event per fire
             trapezoidal velocity profile per block
             Bresenham mixing between motor1/motor2
                    │
                    ▼
                 STEP pins
```

### CoreXY-aware acceleration (this is the important part)

The same motor acceleration does *not* produce the same Cartesian tip
acceleration in every direction. For a move along `(ux, uy)`, the faster
motor travels `max(|ux − uy|, |ux + uy|)` motor-mm per tip-mm: 1 on pure X/Y,
**√2 on ±45° diagonals**.

So if we naively clamp acceleration in motor space, the tip would get full
accel on axis moves, 1/√2 on diagonals and something else at every other
angle — discontinuous Cartesian accel at block boundaries, which means
cogging, belt ringing and corner artefacts.

**What this firmware does instead:**

1. Feedrates, junction deviation, and the trapezoidal profile are all planned
   in **Cartesian tip-space** (mm, mm/s, mm/s²) — what determines how the
   drawing looks.
2. Per block, the motor load (above) clamps the block's acceleration to
   `min($120, $122 / load)` and its speed to `min($110, $112 / load)`.
3. The stepper ISR generates "step events" at the rate the Cartesian profile
   asks for; Bresenham distributes each event to motor1, motor2, both, or
   neither, based on the integer step deltas.

Along any straight line the tip accelerates at a single constant rate, which
may be lower than requested to respect motor limits. Corners follow the
junction-deviation model in Cartesian, so cornering speed follows the *path*
geometry, not the motor mix. Pure X/Y moves are therefore the *fastest*
directions on Blot and ±45° diagonals the slowest — the opposite of a
Cartesian printer.

## Soft limits

There are no limit switches, so nothing physically stops the carriage — a
move past the frame is a crash at up to 16000 mm/min that the machine can
neither detect nor recover from. Soft limits are the only guard, and they're
on by default (`$20`).

The check lives in `plan_buffer_line()`, the one function every move goes
through (job lines and the return to origin), so nothing can bypass it. Out
of range rejects rather than clamps: clamping would silently deform the
drawing and carry on, while a rejection stops the print at the first bad move
(and the web UI says so).

Limits apply to **machine** coordinates, which start at (0, 0) wherever the
pen sits at power-on. `G92` moves the *work* origin, not the machine's, so an
origin set mid-bed genuinely reduces how far you can draw. The envelope is
`$130` × `$131`, default 125 × 125 mm.

## Power and wear behaviour

Deliberate, because this machine is meant to be left plugged in:

- **Event-driven, idle is silent** (see above): no polling, no timers.
- **CPU at 80 MHz when fully idle** (WiFi's floor), back to 240 MHz before
  any motion — the step ISR's timing assumes it.
- **Motors release when idle.** A stationary energised stepper is its worst
  thermal case — rated current, no back-EMF, no airflow — and a plotter has
  no gravity load to hold. Once there's no job and nothing queued, the
  drivers are switched off; a job switches them on before its first move. A
  paused job keeps holding, or the resumed print would be offset.
- **The servo stops pulsing** once the pen has arrived (see above).
- **WiFi modem-sleep unless a page is open.** Each open page holds the /events
  stream; the radio is fully awake while any does (requests answered at once,
  not at the next beacon) and dozes when the last closes. Printing never needs
  it awake: the job streams from flash on the other core.
- **Networking is the bare minimum** for the homelab proxy: IPv4 only, and an
  mDNS A record for `permablot.local` with no service advertisement.
- **No logging and no USB serial driver.**
- **Flash writes only when settings actually change.**

## Building and testing

```bash
pio run              # compile (must be warning-free)
pio run -t upload    # flash firmware
pio run -t uploadfs  # flash the web UI in data/ to LittleFS
nix shell nixpkgs#gcc -c test/host/run.sh   # host simulation
```

`src/wifi_config.h` is required and gitignored — copy
`src/wifi_config.h.example` and fill it in. A missing file is a hard
`#error`, because otherwise the board silently has no network and it looks
like a WiFi bug much later.

`test/host/` runs the real planner, step ISR, servo ISR, parser, job runner
and settings on the host against simulated timers, pins and flash, and checks
every pin edge (pulse widths and spacing, DIR never under a high STEP, no
steps with the drivers off or the CPU slowed, no motion while the pen
travels, stops and starts ramped) plus each job end to end against a
reference reading of its G-code. It can't see real-hardware timing inside an
ISR, so bench-testing is still the last word.

Partition layout is in `partitions.csv`: one 1.25 MB factory app (no OTA) and a
~6.7 MB LittleFS for the web assets and the current job. Changing the table
needs a full `upload` *and* `uploadfs`; the job file doesn't survive it.

## Testing on bench before plotting

Before real art: upload a small square from the web UI with the pen out,
check the carriage traces it and returns, then with a pen check the lines
close. The sticker tool's output is a good second test.

## Known limitations

Deliberate compromises, not bugs:

- **Feed hold decelerates across blocks** (the rate is rescaled per block via
  `events_per_mm_q8`), but parks at a pen block rather than running it
  mid-hold. The planner already brings speed to zero there. It stops once
  down to the speed a start from rest begins at, rather than crawling the
  last fraction toward zero.
- **`G92` offsets accumulate** within a job. Generators start with
  `G92 X0 Y0` after the pen is positioned.
- **A stop preserves motor position**: the planner is re-anchored to where
  the motors physically are, not a phantom (0, 0), before returning to the
  job's origin.
- **Motor-step rounding is bounded at ±0.5 step.** The planner rounds each
  block's motor delta relative to the *absolute* target, so endpoint error is
  ±0.00625 mm however many segments a path has — no √N drift.
